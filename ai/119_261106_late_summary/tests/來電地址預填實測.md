# 來電地址預填實測

日期：2026-11-05

用真正的受理引擎 `SopEngine119.run()` 跑完四通。來電資料走 `fetch_incoming_caller()`，只改模擬內容，沒有跳過取號。分類器用關鍵詞備援（這幾句都明確是救護）。開場白有三句隨機，這次固定抽到「119 您好，請問是需要消防車，還是救護車」。地址階段之後主動結束，沒有繼續問病情。

地址驗測打的是 `http://192.168.5.120:8088/api/AddrCheck/Verify`。這台機器連不上，每次約 2.5 秒逾時。所以「答是之後標成已確認、不再問第二次」這一步在這次實測裡走不到，引擎改走原本的驗測失敗重問。

模擬地址都是「新北市板橋區文化路一段100號」。

## 行動

號碼 `0912-345-678`。開口時槽位只有「板橋區」，沒有路名和門牌。

- 系統：119 您好，請問是需要消防車，還是救護車（槽：板橋區）
- 報案人：我要救護車，有人受傷了
- 系統：請先告訴我地址？幾樓？（槽：板橋區）
- 報案人：板橋區文化路一段100號5樓
- 系統：不好意思，地址我這邊對不起來，麻煩再說一次事發地點？（槽：空。驗測逾時後，原流程先清掉再重問）
- 報案人：是
- 系統：請問現場發生什麼狀況？（槽：板橋區文化路一段100號5樓）

沒有出現「請問是某某地址嗎？」。結束時地址未確認，原因是驗測逾時，不是號碼判斷。

## 市話同意

號碼 `02-29681234`。開口第一句故意講了另一個地點「中和區景平路100號」。核對前槽位仍是 API 的文化路，沒有被這句合併掉。

- 系統：119 您好，請問是需要消防車，還是救護車（槽：新北市板橋區文化路一段100號）
- 報案人：我在中和區景平路100號，有人受傷，我要救護車
- 系統：請問是新北市板橋區文化路一段100號這個地址嗎？（槽：新北市板橋區文化路一段100號）
- 報案人：是
- 系統：不好意思，地址我這邊對不起來，麻煩再說一次事發地點？（槽：空）

沒有問「請先告訴我地址」，也沒有問「確定是這個地址嗎？」。同意之後驗測逾時，原流程把地址清掉準備重問；這通在重問時結束，所以最後槽位是空的，也沒有標成已確認。

## 市話否認

號碼 `0229681234`。

- 系統：119 您好，請問是需要消防車，還是救護車（槽：新北市板橋區文化路一段100號）
- 報案人：我要救護車，有人受傷了
- 系統：請問是新北市板橋區文化路一段100號這個地址嗎？（槽：新北市板橋區文化路一段100號）
- 報案人：不是
- 系統：那麻煩告訴我正確的地址（槽：空。預填已清掉）
- 報案人：中和區景平路100號5樓
- 系統：不好意思，地址我這邊對不起來，麻煩再說一次事發地點？（槽：空）
- 報案人：是
- 系統：請問現場發生什麼狀況？（槽：新北市板橋區文化路一段100號）

「中和區景平路100號5樓」有抽進來，失敗回報寫著：報案人講過「新北市板橋區文化路一段100號、中和區景平路100號5樓」。重問時報案人只答「是」，抽不到新地址。驗測失敗後的既有還原會留下較完整的那一筆，所以槽位回到 API 的文化路，而且未確認。

## 這次沒測到的

答「是」而且驗測通過之後，應直接說「已確認地址。」並標成已確認，不再問第二次。這次驗測服務逾時，這條沒有在實機上走完。
