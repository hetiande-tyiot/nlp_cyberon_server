# 119 智能報案受理系統 — 操作說明

本說明涵蓋目前版本的 SOP 對話引擎、次類別 Handler、Streamlit 介面，以及模型路徑配置與日常操作。

---

## 1. 系統概覽

本系統模擬台灣 119 報案受理流程，目前支援四條主要對話路徑：

| 路徑 | 進入條件 | 流程 | 結束 result |
|------|----------|------|-------------|
| **救護** | 主分類 = 救護 | 地址 → 子分類 → 13 個次類別專屬 SOP | `dispatched` |
| **火警** | 主分類 = 火警 | 地址 → 初期研判 → 四類燃燒標的分流 | `dispatched` |
| **緊急救援** | 主分類 = 緊急救援 | 地址 → 通用問答（暫不做子類識別） | `dispatched` |
| **局內回報** | 首句含「分隊回報／局內回報／同仁回報」（**在主分類之前**分流） | 現場回報 或 支援請求 | `report_recorded`／`support_dispatched` |

上述以外的主類別，記錄後提示轉接專人並以 `dispatched` 結束。任一路徑中地址校驗或覆誦失敗，都會轉為 `human_transfer`。

### 架構原則

| 元件 | 職責 |
|------|------|
| **SOP 引擎** (`sop_119_engine.py`) | 主流程：開場 → 局內回報判斷 → 主分類 → 地址確認 → 依主類別分流 → 摘要 → 報案人訊息 |
| **次類別 Handler** (`handlers/`) | 各救護子類的專屬問答順序、觸發情境、OHCA 判定與報案人訊息 |
| **主類別通用 Handler** (`handlers/火警通用.py`、`handlers/緊急救援通用.py`) | 火警／緊急救援的問答順序；**不註冊在 `_REGISTRY`**，由引擎的 `_run_火警()`／`_run_緊急救援()` 直接 import |
| **LLM 抽取器** (`llm_extractor_119.py`) | 從報警人回答抽取欄位、生成案情摘要／分析報告（**不決定**下一句問什麼） |
| **主分類器** (`inference_pipeline.py`) | MacBERT 判斷火災／救護等主類別 |
| **子分類器** (`classifier_with_llm.py`) | MacBERT 判斷救護／火警子類（`build_classifiers` 只建這兩類） |
| **關鍵詞直判** (`subcategory_keywords_119.py`) | 高貼合子類關鍵詞優先定型（置信度 1.0），未命中再走分類器 |
| **重要標籤** (`important_tags_119.py`) | 每輪掃描報警人輸入，比對重要標籤白名單並合併（見下方「重要標籤」） |
| **欄位標籤** (`case_field_labels_119.py`) | 右欄欄位的顯示名稱對照 |
| **Streamlit UI** (`app_119.py`) | 雙欄介面：左側對話、右側欄位面板 |
| **HTTP API** (`sop_api_server.py`) | FastAPI 服務（`sop119.service`，port 8200），與 Streamlit 共用同一套引擎 |

> **重要**：LLM 只負責「抽取」；對話順序由引擎腳本 + Handler 固定。已抽取的欄位會自動跳過對應問題。

### 地址提問、分類與確認

每一則報警人回答都會先執行 LLM 全欄位抽取，再由固定規則按下列五類地點處理：

| 類別 | 完整條件與校驗 |
|------|----------------|
| 門牌地址 `address` | 必須包含行政區；缺少時最多追問兩遍。完成後呼叫轄區 API，僅非空 `officeName` 視為有效 |
| 交叉路口 `intersection` | 路口、巷口均需兩條道路名稱；缺第二條時最多追問兩遍 |
| 特殊地標 `landmark` | 仅与 `scripts/landmarks.xlsx` 的「地標名稱／別名」比对 |
| 高速公路 `highway` | 必須有高速公路名稱、南向或北向、公里數 |
| 捷運車站 `mrt` | 与 `scripts/MRTstation.csv` 第二列（cp950 编码）比对 |

抽取不到时会再问一遍；API、地标或捷运名单校验失败时，会要求重新提供一次完整地点。最终仍失败，案件会设置 `address_suspect_error=true`，Streamlit 显示地址错误标签，并以 `human_transfer` 转接专人。地址覆诵也必须得到明确确认，不再自动强制确认。

地标表格式固定为：

| 地標名稱 | 別名 | 地址 |
|----------|------|------|
| 板橋大觀市場 | 大觀市場、板橋市場 | 新北市板橋區… |

别名可用 `、 , ， ; ； / ／` 分隔。空模板不会接受任何地标，部署前应填入实际资料。

### 全類型通用標記（ImportantCase／ImportantTag／NeedPolice）

**每一輪**報警人輸入除了 LLM 抽取外，還會由 `important_tags_119.match_important_tags()` 以白名單直接比對原話（`sop_119_engine.py` 的 `_extract_all_fields_from_reply()`）。

| 欄位 | 型別 | 更新規則 |
|------|------|----------|
| `ImportantCase` | `int` 0／1／2 | **可升可降**，依本輪明確證據直接覆寫 |
| `ImportantTag` | `List[str]` | **只增不減**，`merge_important_tags()` 依本輪順序追加去重 |
| `NeedPolice` | `Optional[bool]` | 明確布林證據才覆寫，可被後續更正 |

**ImportantCase 等級**：`0` 預設、`1` 一般處理、`2` 緊急處理。允許降級是刻意的 —— 報警人更正誤聽的關鍵詞時（如「不是持刀，是賭博」），等級必須能跟著降回來。只接受整數 0／1／2，`True`／`False` 與範圍外的值一律忽略（`True` 在 Python 中等於 `1`，若不擋會被誤當成降級）。

**ImportantTag 白名單**（`IMPORTANT_TAGS`，目前 19 個，會持續擴充）：槍聲、殺人、跳樓、賭博、自殺、上吊、槍枝、毒品、持械、持刀、持槍、擄人、砍人、屍體、毒駕、性侵、非法拘禁、救命、強盜。

- 目前白名單內的詞**都屬於等級 2（緊急）**
- 只保留白名單內的值，LLM 抽出白名單以外的詞會被丟棄；擴充直接追加至 `IMPORTANT_TAGS`
- 標籤只增不減：同一通電話先後提到「持刀」與「賭博」，兩者都保留

> ⚠️ **已知不一致**：`ImportantCase` 可因更正而降級，但 `ImportantTag` 目前不會移除已寫入的標籤。報警人說「不是持刀，是賭博」後，等級會降到 1，但 `持刀` 標籤仍留在清單中。

**NeedPolice**：是否需轉介110。案情涉及警務（持械、砍人、鬥毆、槍聲、賭博、毒品、性侵、強盜、擄人、非法拘禁、屍體、毒駕等）或報警人明確要求警方到場時為 `true`；明確表示不用報警為 `false`；僅提到119、救護車、消防車、一般疾病或意外受傷則為 `null`。

Streamlit 右欄的「通用標記」面板會顯示上述三個欄位，`ImportantTag` 以徽章呈現。

### 局內回報流程

首句經 `_is_internal_report()` 判斷，命中即**在主分類之前**分流進 `_run_局內回報()`。

- **觸發關鍵詞**：`分隊回報`、`局內回報`／`局内回报`、`同仁回報`／`同仁回报`（比對前先移除空白）
- 開場問「長官您好，有什麼需要中心協助嗎？」，接著由 `_detect_report_request_type()` 判定兩種需求：

| 需求類型 | 觸發關鍵詞 | 流程 | result |
|----------|------------|------|--------|
| **現場回報** | `現場回報`／`回報現場`／`回報案情`（及簡體） | 記錄地址 + `field_report_content` → 「收到，為您記錄。」 | `report_recorded` |
| **支援請求** | `要車`／`增派`／`加派`／`支援車`／`支援車輛` | 記錄地址 → 問車種與台數 → **覆誦確認**（可更正後重問）→ 派遣 | `support_dispatched` |

- 兩者可在**同一通電話**中接續：完成現場回報後若報案人表示還有需求，會重新分類並轉入支援請求流程
- 相關欄位：`call_type`、`report_request_type`、`field_report_content`、`support_vehicle_type`、`support_vehicle_count`、`support_request_confirmed`
- `call_type` 一旦定為「局內回報」就不會被後續一般案情描述改回去

### 線程架構（Streamlit）

```
主線程（UI）  ←→  input_q / output_q  ←→  工作線程（engine.run()）
```

- `input_q`：使用者輸入 → 引擎
- `output_q`：引擎對話／欄位更新 → UI

## 3. 環境依賴

### Python 套件

本機使用 `llmenv`（Python 3.12），一律以 `./llmenv/bin/pip` 安裝：

```bash
cd /home/cyberon2/nlp_cyberon_server
./llmenv/bin/pip install streamlit torch transformers numpy openpyxl
./llmenv/bin/pip install streamlit-autorefresh   # 處理中自動刷新（未裝會退回 sleep+rerun 忙輪詢）

# LLM（GGUF）— 需 GPU 時建議帶 CUDA
CMAKE_ARGS='-DGGML_CUDA=on' ./llmenv/bin/pip install llama-cpp-python==0.3.23 \
    --force-reinstall --no-cache-dir
```

`streamlit` 會連帶裝上 `pandas`、`pyarrow`、`altair`、`protobuf` 等；若 8200 服務對某些套件版本敏感，升級後請先跑一次冒煙測試再重啟 `sop119.service`。

### 地址轄區 API

默认调用：

```text
http://61.216.64.19:8055/Template/Office/data?addr=新北市新店區中央路133巷
```

可用环境变量覆盖：

```bash
export JURISDICTION_API_URL="http://61.216.64.19:8055/Template/Office/data"
export JURISDICTION_API_TIMEOUT="2.5"
```

API 响应只有 `officeName` 非空时才通过；返回空值或网络异常均会要求重报一次，仍失败则显示地址错误标签并转接专人。

### 硬體建議

| 元件 | 建議 |
|------|------|
| MacBERT 分類器 | CPU 可運行；有 CUDA 更快 |
| GGUF LLM | 建議 GPU（`n_gpu_layers=-1` 全量卸載） |
| 記憶體 | LLM 模型約需數 GB 顯存／記憶體 |

## 4. 模型路徑配置（重點）

底層模組（`inference_pipeline.py`、`classifier_with_llm.py`、`llm_extractor_119.py`）的預設值仍是**上游開發環境的 `/root/autodl-tmp/models/`**。本機不使用該路徑 —— `app_119.py` 與 `sop_api_server.py` 都在載入時以**環境變數**覆蓋，兩者用同一組變數名：

| 環境變數 | 預設值（本機） | 用途 |
|----------|----------------|------|
| `BERT_MODELS_BASE` | `/home/cyberon2/nlp_cyberon_server/ai/` | 主／子分類模型根目錄 |
| `GGUF_MODEL_PATH` | `/home/cyberon2/nlp_cyberon_server/models/TW-119-Model.gguf` | LLM GGUF |
| `BERT_DEVICE` | `cpu` | BERT 跑 CPU，把 VRAM 留給 LLM |
| `GGUF_N_CTX` | `4096` | LLM 上下文長度 |
| `GGUF_N_GPU_LAYERS` | `-1` | GPU 卸載層數，`-1` = 全部 |
| `GGUF_TEMPERATURE` | `0.1` | 生成溫度 |

> 換模型時**改環境變數即可**，不需要動底層模組的預設值。


只有在要讓 `python sop_119_engine.py` 這類 CLI 入口也吃到新路徑時才需要這樣做。

#### 方式 D：LLM 運行參數調整

`LLMExtractor119` 建構參數（`llm_extractor_119.py`）：

| 參數 | 說明 | 預設 |
|------|------|------|
| `model_path` | GGUF 檔案路徑 | 見上 |
| `n_ctx` | 上下文長度 | `4096` |
| `n_gpu_layers` | GPU 卸載層數，`-1` = 全部 | `-1` |
| `temperature` | 生成溫度（抽取建議低溫） | `0.1` |

CPU 環境可設 `n_gpu_layers=0`。

### 4.4 模型載入失敗時的行為

系統採用**靜默降級**策略：

- 主分類器失敗 → 用關鍵詞規則判斷火災／救護
- 子分類器失敗 → 可仍靠關鍵詞直判；否則跳過子類標籤
- LLM 失敗 → 用規則備援抽取；摘要改為模板拼接

對話流程仍可跑通，但欄位抽取準確度會下降。

## 6. Streamlit 介面操作指南

### 6.1 版面說明

| 區域 | 內容 |
|------|------|
| **左欄（2/3）** | 對話氣泡、底部輸入框、「結束流程」按鈕 |
| **右欄（1/3）** | 分類結果、地址、生命征象、患者資訊、報案人訊息、案情摘要、AI 分析報告、流程進度 |

### 6.2 基本操作流程

1. 開啟頁面後，系統自動隨機擇一開場白，例如：**「119 您好，請問是火災還是救護」**
2. 在底部輸入框以報警人口吻回答（可同時帶地址／病情，例如：`救護，路人跌倒了，旁邊沒家屬，地址在…`）。
3. 依提示逐步確認地址、回答次類別專屬問題。
4. 右欄會**即時更新**已抽取的欄位與案情摘要。
5. 流程結束後顯示派車結束語，或 OHCA／轉人工話術。
6. 點擊 **「🔄 重新開始新通話」** 可重置整個 session。
7. 測試中可點 **「⏹ 結束流程」** 主動終止當前 SOP。

### 6.3 右欄功能

- **分類結果**：主類（救護／火警／緊急救援／局內回報）與子類（急病、路倒、車禍等）及置信度
- **事發地址**：含地址型態、是否已確認、校驗狀態、轄區分隊
- **通用標記**：案件重要程度（0/1/2）、AI 重要標籤徽章、是否需轉介110
- **生命征象**：意識／呼吸／腹部起伏（有／無）
- **患者資訊**：性別、年齡、事件描述、目前狀況等（依次類別欄位不同）
- **火警要素**：燃燒標的、火勢、坪數、受困人數、延燒等（僅火警案件顯示）
- **局內回報欄位**：回報類型、現場回報案情、支援車種與台數（僅 `call_type=局內回報` 時顯示）
- **報案人訊息**：姓名、聯繫方式、稱呼、住址（急病／一般受傷會多問住址）
- **案情摘要**：每輪自動更新（不對報案人複誦確認）
- **📊 分析報告**：手動點擊生成初報分析報告，可下載 TXT
- **流程進度**：當前 SOP 階段

### 6.4 等待與同步

LLM 抽取與摘要生成需要時間，輸入後輸入框會暫時禁用，並顯示「本輪輸入處理中…」。

- 若右欄欄位未及時更新，可點 **「同步最新狀態」**
- 已安裝 `streamlit-autorefresh` 時會自動輪詢刷新

### 6.5 OHCA 警示

若意識、呼吸或腹部起伏任一項明確為「無」（依次類別是否走到 S1／S2），系統判定 **OHCA**，會：

- 左欄顯示紅色警示橫幅
- 播放轉人工話術
- 流程以 `ohca_transfer` 結束

> **車禍** 流程無 S1／S2 生命征象問答，不走上述 OHCA 路徑。

### 7.3 共用生命征象（S1／S2）

多數 Handler 呼叫基類方法：

- **S1 意識／呼吸**：已填則跳過；只知一項則只問缺的；任一明確為否 → 立即 OHCA
- **S2 反應／腹部起伏**：已清醒則只問起伏；否則從「叫反應／捏反應／起伏」隨機一題；起伏非「有」→ OHCA

### 7.4 路倒專屬說明（重點）

順序：**S0（發生什麼事）→ S1 → S2 → S4（身邊是否有家屬）→ S6（性別／年齡）**

| 步驟 | 問題（摘要） | 跳過條件 |
|------|--------------|----------|
| S0 | 請問發生什麼事呢？ | `incident_description` 已填 |
| S1 | 有沒有清醒？是否有正常呼吸？ | 意識／呼吸已填（可部分跳過） |
| S2 | 叫／捏反應或肚子起伏 | `abdomen_rise` 已填；已清醒則只問起伏 |
| S4 | 請問身邊是否有家屬？ | `medical_history` 已填（本類存放**家屬在場**，非病史） |
| S6 | 男生還是女生、大約幾歲？ | 性別＋年齡皆已填 |

**S4 跳過邏輯**：提問前會執行 `_ensure_family_from_history`，用家屬專屬規則掃描歷史回答。若報警人稍早已說明（如「旁邊沒家屬」），會寫入 `medical_history=無家屬` 並**跳過**「請問身邊是否有家屬？」。

**觸發情境**：公共場所倒地 → 重複確認地址 +「救護車已經派了。」

### 7.5 測試用對話範例（路倒，正常派車）

| 輪次 | 系統（示意） | 建議回答 |
|------|--------------|----------|
| 1 | 火災還是救護？ | `救護，路人走路跌倒了，旁邊沒家屬` |
| 2 | 請先告訴我地址？樓層？ | `台北市中山北路123號一樓騎樓` |
| 3 | 確定是…地址嗎？ | `對` |
| 4 | （子類定為路倒後）有沒有清醒？是否有正常呼吸？ | `有清醒，有呼吸` |
| 5 | 肚子有沒有起伏／叫有反應嗎？ | `有起伏` |
| — | **S4 應跳過**（因首輪已說旁邊沒家屬） | — |
| 6 | 男生還是女生、大約幾歲？ | `男生，大約70歲` |
| 7 | 姓名與聯繫方式？ | `王小明，0912345678` |

> 若首輪未提家屬，才會出現「請問身邊是否有家屬？」。

### 7.6 欄位自動跳過原則

- 每輪報警人回答都會做 **LLM 跨欄位抽取**；後續問題前再 `_ensure_known_fields_from_history`
- 次類別專屬語意（如路倒的「家屬在場」）若無法靠通用抽取寫入對應欄位，Handler 會在提問前做**專屬補抽**（例：路倒 `_ensure_family_from_history`）

## 8. 程式化整合（開發者）

### 8.1 在 Python 中啟動引擎

```python
import queue, threading
from sop_119_engine import SopEngine119, QueueDialogueIO
from llm_extractor_119 import LLMExtractor119
from inference_pipeline import HierarchicalClassifier
from classifier_with_llm import build_classifiers

input_q  = queue.Queue()
output_q = queue.Queue()
io = QueueDialogueIO(input_q, output_q)

MODELS_BASE = "/home/cyberon2/nlp_cyberon_server/ai/"
GGUF_PATH   = "/home/cyberon2/nlp_cyberon_server/models/TW-119-Model.gguf"

engine = SopEngine119(
    io=io,
    main_classifier=HierarchicalClassifier(models_base=MODELS_BASE, device="cpu"),
    sub_classifiers=build_classifiers(models_base=MODELS_BASE, device="cpu",
                                      enable_llm=False),
    llm_extractor=LLMExtractor119(model_path=GGUF_PATH),
    debug=False,
)

threading.Thread(target=engine.run, daemon=True).start()

# 推送使用者輸入
input_q.put("救護")

# 讀取輸出事件
while True:
    event = output_q.get()
    print(event)
    if event.get("type") == "stopped":
        break
```

### 8.2 output_q 事件格式

| type | 說明 |
|------|------|
| `chat` | `{"role": "assistant"\|"caller", "text": "..."}` |
| `case_update` | `{"case": {...}}` 欄位更新 |
| `classification` | 主／子分類結果（可含 `sub_source`: `keyword`／`classifier`） |
| `stage_update` | SOP 階段變更 |
| `stopped` | 流程結束，`result` 見下表 |
| `error` | 異常訊息 |

`stopped.result` 共 7 種：

| result | 觸發情境 |
|--------|----------|
| `dispatched` | 救護／火警／緊急救援正常派遣完成 |
| `ohca_transfer` | 判定 OHCA，轉人工 |
| `human_transfer` | 地址校驗或覆誦確認失敗，轉人工 |
| `report_recorded` | 局內回報：現場回報已記錄結案 |
| `support_dispatched` | 局內回報：支援請求已派遣 |
| `manual_end` | 操作員按「⏹ 結束流程」主動終止 |
| `error` | 引擎異常 |

## 9. 常見問題排查

### Q1：頁面顯示「主分類器未能載入」／「模型目錄不存在」

- 檢查 `/home/cyberon2/nlp_cyberon_server/ai/TW-119-BERT_main/` 是否存在且含 `label_map.json`
- 若曾自行設過 `BERT_MODELS_BASE`，確認指向的目錄正確
- 確認已安裝 `torch`、`transformers`
- 可暫時忽略，系統會用關鍵詞規則，但欄位抽取會明顯變差

### Q2：頁面顯示「LLM 未能載入」

- 確認 GGUF 檔案路徑正確（見第 4 節）
- 確認已安裝 `llama-cpp-python`
- GPU 環境檢查 CUDA 是否可用；CPU 可設 `n_gpu_layers=0`

### Q3：輸入後長時間無回應

- LLM 首次推理較慢，等待 10–30 秒
- 點「同步最新狀態」
- 查看終端是否有 OOM 或模型錯誤

### Q4：欄位抽取不準

- 確認 LLM 已成功載入（無黃色警告）
- 用 `python sop_119_engine.py --debug` 查看抽取 JSON
- 檢查 `temperature` 是否過高（建議 ≤ 0.15）

### Q5：修改模型路徑後仍用舊模型

Streamlit 會快取模型實例。修改路徑後需：

```bash
# 重啟 Streamlit，或在瀏覽器選單 Clearing cache → Clear resource cache
```

或刪除 Streamlit 快取後重啟。

### Q6：已說明的資訊仍被重複詢問

- 確認該資訊是否寫入對應 skip 欄位（右欄／`--debug`）
- 路倒「家屬」：應由 `_ensure_family_from_history` 補抽；若仍重複，用 `--debug` 查看 `S4_family_from_history`／`skip_S4`
- 修改 Handler 後需**重啟 Streamlit** 才會載入新程式碼

### Q7：想擴展主類別 SOP

`sop_119_engine.py` 的 `_run_main_flow()` 目前已有 `_run_救護()`／`_run_火警()`／`_run_緊急救援()` 三個分支，其餘主類別才走「記錄後轉接專人」。

- **新增主類別**：新增 `_run_{類別}()` 並在 `_run_main_flow()` 的分支中調用；問答順序建議比照 `handlers/火警通用.py` 另開一個 handler
- **擴展救護子類**：走第 2 節 Handler Registry，主流程零改動
- **火警子類**：目前 `_run_火警()` 用 `handlers/火警通用.py` 依燃燒標的（建築物／工廠／車輛／露天野外）分流，不經 `_REGISTRY`
- **緊急救援子類**：目前不做子類識別，只走通用問答

### Q8：子分類總是不準／一直追問「發生什麼事」

- 關鍵詞未命中且分類器置信度 < 0.7 時，最多再問 2 次
