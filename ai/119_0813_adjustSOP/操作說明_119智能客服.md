# 119 智能報案受理系統 — 操作說明

本說明涵蓋目前版本的 SOP 對話引擎、次類別 Handler、Streamlit 介面，以及模型路徑配置與日常操作。

---

## 1. 系統概覽

本系統模擬台灣 119 報案受理流程，目前**完整支援「救護」主類別**下 13 個次類別的專屬 SOP；火警等其他主類別會記錄後提示轉接專人。

### 架構原則

| 元件 | 職責 |
|------|------|
| **SOP 引擎** (`sop_119_engine.py`) | 主流程：開場 → 主分類 → 地址確認 → 子分類 → 委派 Handler → 摘要 → 報案人訊息 |
| **次類別 Handler** (`handlers/`) | 各救護子類的專屬問答順序、觸發情境、OHCA 判定與報案人訊息 |
| **LLM 抽取器** (`llm_extractor_119.py`) | 從報警人回答抽取欄位、生成案情摘要／分析報告（**不決定**下一句問什麼） |
| **主分類器** (`inference_pipeline.py`) | MacBERT 判斷火災／救護等主類別 |
| **子分類器** (`classifier_with_llm.py`) | MacBERT 判斷救護子類 |
| **關鍵詞直判** (`subcategory_keywords_119.py`) | 高貼合子類關鍵詞優先定型（置信度 1.0），未命中再走分類器 |
| **Streamlit UI** (`app_119.py`) | 雙欄介面：左側對話、右側欄位面板 |

> **重要**：LLM 只負責「抽取」；對話順序由引擎腳本 + 次類別 Handler 固定。已抽取的欄位會自動跳過對應問題。

### 地址提問、分類與確認

每一則報警人回答都會先執行 LLM 全欄位抽取，再由固定規則按下列五類地點處理：

| 類別 | 完整條件與校驗 |
|------|----------------|
| 門牌地址 `address` | 必須包含行政區、道路、門牌號；每輪均由 LLM 增量抽取並合併，任一元件缺少時最多追問兩遍。完成後呼叫轄區 API，僅非空 `officeName` 視為有效 |
| 交叉路口 `intersection` | 路口、巷口均需兩條道路名稱；缺第二條時最多追問兩遍 |
| 特殊地標 `landmark` | 仅与 `scripts/landmarks.xlsx` 的「地標名稱／別名」比对 |
| 高速公路 `highway` | 必須有高速公路名稱、南向或北向、公里數 |
| 捷運車站 `mrt` | 与 `scripts/MRTstation.csv` 第二列（cp950 编码）比对 |

門牌地址確認為 `address` 後，每一輪報警人輸入都會再由 LLM 抽取本輪明確提供的區、路、號，與先前元件合併後更新完整地址。缺區追問「請告訴我是那一區？」、缺路追問「請問是什麼路」、缺號追問「請問是幾號」，每項最多兩遍。抽取不到、元件仍不完整，或 API、地標、捷運名單最終校驗失敗時，案件會設置 `address_suspect_error=true`、`ImportantCase=1`、`ImportantTag=["地址搜尋失敗"]`，Streamlit 顯示地址錯誤標籤，並繼續後續流程而不轉接專人。地址覆誦也必須得到明確確認，不再自動強制確認。

地标表格式固定为：

| 地標名稱 | 別名 | 地址 |
|----------|------|------|
| 板橋大觀市場 | 大觀市場、板橋市場 | 新北市板橋區… |

别名可用 `、 , ， ; ； / ／` 分隔。空模板不会接受任何地标，部署前应填入实际资料。

### 線程架構（Streamlit）

```
主線程（UI）  ←→  input_q / output_q  ←→  工作線程（engine.run()）
```

- `input_q`：使用者輸入 → 引擎
- `output_q`：引擎對話／欄位更新 → UI

1. 在 `handlers/` 下新增 `.py`，繼承 `SubCategoryHandler`，實作 `run_subtype_flow`（或覆寫鉤子）
2. 在 `handlers/__init__.py` 的 `_REGISTRY` 登記
3. 主流程 `sop_119_engine.py` **無需改動**

## 3. 環境依賴

### Python 套件

```bash
pip install streamlit torch transformers numpy openpyxl
pip install streamlit-autorefresh   # 可選，用於處理中自動刷新

# LLM（GGUF）— 需 GPU 時建議帶 CUDA
CMAKE_ARGS='-DGGML_CUDA=on' pip install llama-cpp-python==0.3.23 --force-reinstall --no-cache-dir
```

### 地址轄區 API

默认调用：

```text
http://61.216.64.19:8055/Template/Office/data?addr=新北市新店區中央路133巷
```

可用环境变量覆盖：

```bash
export JURISDICTION_API_URL="http://61.216.64.19:8055/Template/Office/data"
export JURISDICTION_API_TIMEOUT="2.5"
```

API 响应只有 `officeName` 非空时才通过；返回空值或网络异常均会要求重报一次，仍失败则显示地址错误标签并转接专人。

### 硬體建議

| 元件 | 建議 |
|------|------|
| MacBERT 分類器 | CPU 可運行；有 CUDA 更快 |
| GGUF LLM | 建議 GPU（`n_gpu_layers=-1` 全量卸載） |
| 記憶體 | LLM 模型約需數 GB 顯存／記憶體 |

## 4. 模型路徑配置（重點）

所有模型預設根目錄為 **`/root/autodl-tmp/models/`**。若模型放在其他位置，需修改下列檔案。

### 4.1 模型目錄結構

部署時應確保以下目錄／檔案存在：

```
/root/autodl-tmp/models/
├── TW-119-BERT_main/                # 主分類（火警/救護/…）
│   ├── config.json
│   ├── label_map.json
│   └── pytorch_model.bin（或 safetensors）
├── TW-119-BERT-sub_救護/            # 救護子分類（程式預設路徑）
│   ├── config.json
│   ├── label_map.json
│   └── ...
├── TW-119-BERT-sub_火警/            # 火警子分類（可選）
│   └── ...
└── TW-119-Model/
    └── TW-119-Model.gguf            # LLM 抽取 / 摘要 / 分析報告
```

可用以下命令檢查：

```bash
ls -la /root/autodl-tmp/models/TW-119-BERT_main/
ls -la /root/autodl-tmp/models/TW-119-BERT-sub_救護/
ls -la /root/autodl-tmp/models/TW-119-Model/TW-119-Model.gguf
```

> 若使用 `TW-119-BERT-sub_救護_new/` 等替代目錄，請在 `classifier_with_llm.py` 的 `build_classifiers(models_base=...)` 或目錄命名邏輯中改為實際路徑。

**命名規則**（已由舊版 `macbert_main` / `macbert_sub_*` 更名）：

| 舊目錄名 | 新目錄名 |
|----------|----------|
| `macbert_main` | `TW-119-BERT_main` |
| `macbert_sub_救護` | `TW-119-BERT-sub_救護` |
| `macbert_sub_火警` | `TW-119-BERT-sub_火警` |
| `macbert_sub_緊急救援` | `TW-119-BERT-sub_緊急救援` |
| `macbert_sub_其他案類` | `TW-119-BERT-sub_其他案類` |

> 主分類目錄為 `TW-119-BERT_main`（`_main` 使用底線）；子分類為 `TW-119-BERT-sub_{類別}`（`sub` 前使用連字號）。

### 4.2 修改位置一覽

| 用途 | 檔案 | 變數 / 參數 | 預設值 |
|------|------|-------------|--------|
| **LLM 抽取 / 摘要** | `llm_extractor_119.py` | `DEFAULT_MODEL_PATH` | `/root/autodl-tmp/models/TW-119-Model/TW-119-Model.gguf` |
| **主分類器** | `inference_pipeline.py` | `HierarchicalClassifier(models_base=...)`；子目錄 `TW-119-BERT_main` | `/root/autodl-tmp/models/` |
| **子分類器** | `classifier_with_llm.py` | `build_classifiers(models_base=...)`；子目錄 `TW-119-BERT-sub_{類別}` | 同上 |
| **Streamlit 載入** | `app_119.py` | `_load_models()` | 呼叫上述預設 |
| **CLI 測試** | `sop_119_engine.py` | `_cli_main()` | 同上 |

### 4.3 修改範例

#### 方式 A：改 LLM 預設路徑（全域生效）

編輯 `llm_extractor_119.py`：

```python
DEFAULT_MODEL_PATH = "/你的路徑/你的模型.gguf"
```

#### 方式 B：改分類器根目錄

編輯 `inference_pipeline.py`：

```python
def __init__(self, models_base: str = "/你的路徑/models/", ...):
```

編輯 `classifier_with_llm.py` 的 `build_classifiers`：

```python
def build_classifiers(
    models_base: str = "/你的路徑/models/",
    llm_model_path: Optional[str] = "/你的路徑/模型.gguf",
    ...
):
```

#### 方式 C：僅在 Streamlit 中自訂（推薦，不動底層預設）

編輯 `app_119.py` 的 `_load_models()`：

```python
MODELS_BASE = "/你的路徑/models/"
LLM_PATH    = "/你的路徑/你的模型.gguf"

@st.cache_resource(show_spinner="正在載入模型，請稍候…")
def _load_models():
    ...
    main_clf = HierarchicalClassifier(models_base=MODELS_BASE)
    ...
    sub_clf = build_classifiers(models_base=MODELS_BASE, enable_llm=False)
    ...
    llm = LLMExtractor119(model_path=LLM_PATH, n_gpu_layers=-1)
```

#### 方式 D：LLM 運行參數調整

`LLMExtractor119` 建構參數（`llm_extractor_119.py`）：

| 參數 | 說明 | 預設 |
|------|------|------|
| `model_path` | GGUF 檔案路徑 | 見上 |
| `n_ctx` | 上下文長度 | `4096` |
| `n_gpu_layers` | GPU 卸載層數，`-1` = 全部 | `-1` |
| `temperature` | 生成溫度（抽取建議低溫） | `0.1` |

CPU 環境可設 `n_gpu_layers=0`。

### 4.4 模型載入失敗時的行為

系統採用**靜默降級**策略：

- 主分類器失敗 → 用關鍵詞規則判斷火災／救護
- 子分類器失敗 → 可仍靠關鍵詞直判；否則跳過子類標籤
- LLM 失敗 → 用規則備援抽取；摘要改為模板拼接

對話流程仍可跑通，但欄位抽取準確度會下降。

## 5. 啟動方式

### 5.1 Streamlit 互動介面（推薦）

```bash
cd /root/work/119
streamlit run app_119.py
```

瀏覽器開啟後（預設 `http://localhost:8501`）即可操作。

**首次啟動**會載入三類模型，頁面頂部顯示「正在載入模型，請稍候…」，視硬體需等待數十秒至數分鐘。

指定埠號：

```bash
streamlit run app_119.py --server.port 8502
```

遠端存取（若需從外網連線）：

```bash
streamlit run app_119.py --server.address 0.0.0.0 --server.port 8501
```

### 5.2 CLI 終端測試

適合開發除錯，不需瀏覽器：

```bash
cd /root/work/119

# 完整模式（載入所有模型）
python sop_119_engine.py

# 僅測對話流程，不載入模型
python sop_119_engine.py --no-main-clf --no-sub-clf --no-llm

# 載入 LLM 並印出除錯資訊
python sop_119_engine.py --debug

# 組合使用
python sop_119_engine.py --no-sub-clf --debug
```

CLI 參數說明：

| 參數 | 說明 |
|------|------|
| `--no-main-clf` | 不載入主分類器 |
| `--no-sub-clf` | 不載入子分類器 |
| `--no-llm` | 不載入 LLM |
| `--debug` | 在 stderr 印出 LLM 輸入／輸出與 skip／抽取除錯 |

結束後會在終端印出 JSON 格式的最終案件資訊。

## 6. Streamlit 介面操作指南

### 6.1 版面說明

| 區域 | 內容 |
|------|------|
| **左欄（2/3）** | 對話氣泡、底部輸入框、「結束流程」按鈕 |
| **右欄（1/3）** | 分類結果、地址、生命征象、患者資訊、報案人訊息、案情摘要、AI 分析報告、流程進度 |

### 6.2 基本操作流程

1. 開啟頁面後，系統自動隨機擇一開場白，例如：**「119 您好，請問是火災還是救護」**
2. 在底部輸入框以報警人口吻回答（可同時帶地址／病情，例如：`救護，路人跌倒了，旁邊沒家屬，地址在…`）。
3. 依提示逐步確認地址、回答次類別專屬問題。
4. 右欄會**即時更新**已抽取的欄位與案情摘要。
5. 流程結束後顯示派車結束語，或 OHCA／轉人工話術。
6. 點擊 **「🔄 重新開始新通話」** 可重置整個 session。
7. 測試中可點 **「⏹ 結束流程」** 主動終止當前 SOP。

### 6.3 右欄功能

- **分類結果**：主類（救護／火警）與子類（急病、路倒、車禍等）及置信度
- **事發地址**：含是否已確認
- **生命征象**：意識／呼吸／腹部起伏（有／無）
- **患者資訊**：性別、年齡、事件描述、目前狀況等（依次類別欄位不同）
- **報案人訊息**：姓名、聯繫方式、住址（急病／一般受傷會多問住址）
- **案情摘要**：每輪自動更新（不對報案人複誦確認）
- **📊 分析報告**：手動點擊生成初報分析報告，可下載 TXT
- **流程進度**：當前 SOP 階段

### 6.4 等待與同步

LLM 抽取與摘要生成需要時間，輸入後輸入框會暫時禁用，並顯示「本輪輸入處理中…」。

- 若右欄欄位未及時更新，可點 **「同步最新狀態」**
- 已安裝 `streamlit-autorefresh` 時會自動輪詢刷新

### 6.5 OHCA 警示

若意識、呼吸或腹部起伏任一項明確為「無」（依次類別是否走到 S1／S2），系統判定 **OHCA**，會：

- 左欄顯示紅色警示橫幅
- 播放轉人工話術
- 流程以 `ohca_transfer` 結束

> **車禍** 流程無 S1／S2 生命征象問答，不走上述 OHCA 路徑。

## 7. 救護 SOP 對話流程（目前版本）

### 7.1 主流程（所有救護案件共用）

```
開場（火災/救護，三句隨機）
    ↓ 主分類（MacBERT 或關鍵詞備援）
確認地址（首輪已說則跳過詢問；複讀確認，最多約 3 次）
    ↓ 「已確認地址，救護車已派出了喔。」
子分類：關鍵詞直判優先 → 否則 MacBERT
    ↓（分類器置信度 < 0.7 時最多再追問 2 次「麻煩發生了什麼事？」）
委派次類別 Handler.run_subtype_flow(...)
    ↓（已抽取欄位自動跳過對應問題；觸發情境可插播指引）
案情摘要回填（僅更新 UI，不對報案人複誦）
    ↓
收集報案人訊息 → 結束語 → dispatched
```

### 7.2 已註冊次類別（13）

| 次類別 | Handler | 典型問題順序 | 報案人問住址 | OHCA |
|--------|---------|--------------|--------------|------|
| 路倒 | `路倒.py` | S0→S1→S2→S4→S6 | 否 | S1+S2 |
| 急病 | `急病.py` | S0→S1→S2→S6 | **是** | S1+S2 |
| 車禍 | `車禍.py` | S0→安全叮嚀→S3→S4×4 | 否 | 無 |
| 一般受傷 | `一般受傷.py` | S0→S1→S2→S4×2→S6 | **是** | S1+S2 |
| 精神異常 | `精神異常.py` | S0→S1→S4×3 | 否 | 僅 S1 |
| 打架受傷 | `打架受傷.py` | S0→S1→S2→S6→S4 | 否 | S1+S2 |
| 吞食藥物 | `吞食藥物.py` | S0→S1→S2→S4→S6 | 否 | S1+S2 |
| 墜落傷 | `墜落傷.py` | S0→S1→S2→S6→S4×3 | 否 | S1+S2 |
| 孕婦急產 | `孕婦急產.py` | S0→S1→S4×7 | 否 | 僅 S1 |
| 燒炭 | `燒炭.py` | S0→S1→S2→S6→S4 | 否 | S1+S2 |
| 燒燙傷 | `燒燙傷.py` | S0→S1→S4 | 否 | 僅 S1 |

| 上吊 | `上吊.py` | S0→S3→S1→S6 | 否 | 僅 S1 |

未命中 Registry 的子類 → 使用基類通用流程（生命征象 3 問 + 患者資訊 3 問）。

### 7.3 共用生命征象（S1／S2）

多數 Handler 呼叫基類方法：

- **S1 意識／呼吸**：已填則跳過；只知一項則只問缺的；任一明確為否 → 立即 OHCA
- **S2 反應／腹部起伏**：已清醒則只問起伏；否則從「叫反應／捏反應／起伏」隨機一題；起伏非「有」→ OHCA

### 7.4 路倒專屬說明（重點）

順序：**S0（發生什麼事）→ S1 → S2 → S4（身邊是否有家屬）→ S6（性別／年齡）**

| 步驟 | 問題（摘要） | 跳過條件 |
|------|--------------|----------|
| S0 | 請問發生什麼事呢？ | `incident_description` 已填 |
| S1 | 有沒有清醒？是否有正常呼吸？ | 意識／呼吸已填（可部分跳過） |
| S2 | 叫／捏反應或肚子起伏 | `abdomen_rise` 已填；已清醒則只問起伏 |
| S4 | 請問身邊是否有家屬？ | `medical_history` 已填（本類存放**家屬在場**，非病史） |
| S6 | 男生還是女生、大約幾歲？ | 性別＋年齡皆已填 |

**S4 跳過邏輯**：提問前會執行 `_ensure_family_from_history`，用家屬專屬規則掃描歷史回答。若報警人稍早已說明（如「旁邊沒家屬」），會寫入 `medical_history=無家屬` 並**跳過**「請問身邊是否有家屬？」。

**觸發情境**：公共場所倒地 → 重複確認地址 +「救護車已經派了。」

### 7.5 測試用對話範例（路倒，正常派車）

| 輪次 | 系統（示意） | 建議回答 |
|------|--------------|----------|
| 1 | 火災還是救護？ | `救護，路人走路跌倒了，旁邊沒家屬` |
| 2 | 請先告訴我地址？樓層？ | `台北市中山北路123號一樓騎樓` |
| 3 | 確定是…地址嗎？ | `對` |
| 4 | （子類定為路倒後）有沒有清醒？是否有正常呼吸？ | `有清醒，有呼吸` |
| 5 | 肚子有沒有起伏／叫有反應嗎？ | `有起伏` |
| — | **S4 應跳過**（因首輪已說旁邊沒家屬） | — |
| 6 | 男生還是女生、大約幾歲？ | `男生，大約70歲` |
| 7 | 姓名與聯繫方式？ | `王小明，0912345678` |

> 若首輪未提家屬，才會出現「請問身邊是否有家屬？」。

### 7.6 欄位自動跳過原則

- 每輪報警人回答都會做 **LLM 跨欄位抽取**；後續問題前再 `_ensure_known_fields_from_history`
- 次類別專屬語意（如路倒的「家屬在場」）若無法靠通用抽取寫入對應欄位，Handler 會在提問前做**專屬補抽**（例：路倒 `_ensure_family_from_history`）

## 8. 程式化整合（開發者）

### 8.1 在 Python 中啟動引擎

```python
import queue, threading
from sop_119_engine import SopEngine119, QueueDialogueIO
from llm_extractor_119 import LLMExtractor119
from inference_pipeline import HierarchicalClassifier
from classifier_with_llm import build_classifiers

input_q  = queue.Queue()
output_q = queue.Queue()
io = QueueDialogueIO(input_q, output_q)

engine = SopEngine119(
    io=io,
    main_classifier=HierarchicalClassifier(models_base="/root/autodl-tmp/models/"),
    sub_classifiers=build_classifiers(enable_llm=False),
    llm_extractor=LLMExtractor119(),
    debug=False,
)

threading.Thread(target=engine.run, daemon=True).start()

# 推送使用者輸入
input_q.put("救護")

# 讀取輸出事件
while True:
    event = output_q.get()
    print(event)
    if event.get("type") == "stopped":
        break
```

### 8.2 output_q 事件格式

| type | 說明 |
|------|------|
| `chat` | `{"role": "assistant"\|"caller", "text": "..."}` |
| `case_update` | `{"case": {...}}` 欄位更新 |
| `classification` | 主／子分類結果（可含 `sub_source`: `keyword`／`classifier`） |
| `stage_update` | SOP 階段變更 |
| `stopped` | 流程結束，`result`: `dispatched`／`ohca_transfer`／`manual_end`／`error` |
| `error` | 異常訊息 |

## 9. 常見問題排查

### Q1：頁面顯示「主分類器未能載入」

- 檢查 `/root/autodl-tmp/models/TW-119-BERT_main/` 是否存在且含 `label_map.json`
- 確認已安裝 `torch`、`transformers`
- 可暫時忽略，系統會用關鍵詞規則

### Q2：頁面顯示「LLM 未能載入」

- 確認 GGUF 檔案路徑正確（見第 4 節）
- 確認已安裝 `llama-cpp-python`
- GPU 環境檢查 CUDA 是否可用；CPU 可設 `n_gpu_layers=0`

### Q3：輸入後長時間無回應

- LLM 首次推理較慢，等待 10–30 秒
- 點「同步最新狀態」
- 查看終端是否有 OOM 或模型錯誤

### Q4：欄位抽取不準

- 確認 LLM 已成功載入（無黃色警告）
- 用 `python sop_119_engine.py --debug` 查看抽取 JSON
- 檢查 `temperature` 是否過高（建議 ≤ 0.15）

### Q5：修改模型路徑後仍用舊模型

Streamlit 會快取模型實例。修改路徑後需：

```bash
# 重啟 Streamlit，或在瀏覽器選單 Clearing cache → Clear resource cache
```

或刪除 Streamlit 快取後重啟。

### Q6：已說明的資訊仍被重複詢問

- 確認該資訊是否寫入對應 skip 欄位（右欄／`--debug`）
- 路倒「家屬」：應由 `_ensure_family_from_history` 補抽；若仍重複，用 `--debug` 查看 `S4_family_from_history`／`skip_S4`
- 修改 Handler 後需**重啟 Streamlit** 才會載入新程式碼

### Q7：想擴展火警等其他主類 SOP

在 `sop_119_engine.py` 的 `_run_main_flow()` 中，目前非「救護」僅提示轉接。可新增 `_run_火警()` 等並在分支中調用；救護子類擴展則走第 2 節 Handler Registry。

### Q8：子分類總是不準／一直追問「發生什麼事」

- 關鍵詞未命中且分類器置信度 < 0.7 時，最多再問 2 次
- 可在 `subcategory_keywords_119.py` 為高貼合詞彙加規則（繁簡建議一起加）
- 確認子分類模型目錄與 `label_map.json` 標籤與 Handler 名稱一致（如 `路倒`、`急病`；模型若輸出 `孕婦待產`，需與 Registry 鍵名對齊或做別名映射）
