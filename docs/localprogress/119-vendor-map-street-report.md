# 給 vendor：`map_street.json` / `map_city.json` 生成問題回報

2026-09-05．來源：119 系統上線後的真實通話 ＋ `map_street.json` 全表 25439 條
逐條 addrCheck 驗證

---

## 摘要

`map_street.json` **整體品質良好**——全表逐條驗證，25416 / 25439（99.9%）的映射
是合理的。但有 **21 條（0.08%）的來源本身就是真實存在的路名**，套用會把報案人
講對的地址改成另一條街。其中一條已在真實火警通話造成**派遣地址完全錯誤**。

生成方式應該是：以真實路名清單為目標（1707 個不重複目標，平均每個對應 14.9 個
來源變體），用 `ese.py` 的臺語羅馬拼音＋加權編輯距離產生可能被聽錯的變體。
方向正確，只差一層「變體本身是否已是真實路名」的過濾。

`map_city.json` 有同性質的 7 條（比例較高，4188 條中 7 條把真實行政區映射掉）。

---

## 問題一：來源本身就是真實路名（會把講對的改掉）

### 真實案例（2026-09-04 20:57，火警，已派遣）

報案人說：**「重陽路跟新北大道的岔路交叉路口」**
系統存檔：**`板橋區三和路與新新新新新新思源路口`**

```
"重陽路":     "三和路"     ← 三重區真的有重陽路（addrCheck：一段、二段、四段）
"新北大道路": "思源路"     ← 三重區有新北大道一段、新莊區有三/四段
```

`重陽路` 與 `三和路` **在三重區同時存在，是兩條不同的街**。

### 逐條驗證結果（全表）

已對 `map_street.json` **全表 25439 條逐條查詢 addrCheck**（0 筆查詢失敗），
判準是「API 回傳的地址裡是否含原路名」。結果：

| | 條數 | 佔比 |
|---|---|---|
| 來源本身就是真實路名（映射會改掉正確的路）| **21** | 0.08% |
| 來源確實查無（映射合理）| 25416 | 99.9% |
| 無法判定（需人工）| 2 | — |

**整體品質良好**，需要修正的是這 21 條：

```
"中山北路": "中正北路"    "凌雲路":   "成泰路"      "北深路":   "松柏街"
"嘉義縣路": "佳園路"      "國福路":   "五福路"      "寶安街":   "保安街"
"後洲路":   "後州路"      "榮華路":   "文化路"      "水漾路":   "三陽路"
"永安北路": "仁安街"      "港東路":   "圓通路"      "濱海路":   "淡金路"
"篤行路":   "存德街"      "興南路":   "復興路"      "花園一路": "湖子內路"
"莊園路":   "中原路"      "萬壽路":   "萬安街"      "豐華路":   "光華路"
"重陽路":   "三和路"      "金美街":   "集美街"      "雙十路":   "吳鳳路"
```

無法判定的 2 條（hint 未回傳路名，需貴方確認）：`中正零層路`、`中港東路`。

⚠️ **判斷不能只看 `reason`**：`ambiguous` 多半是「來源查無，但同音的有好幾條」，
`valid` 也可能是 API 模糊比對到別條路。例如
`「中小街1號」查無此路。同音的「忠孝街」在 三峽區…都有` 的 reason 是 ambiguous，
但中小街本身並不存在。我方初版判斷用 reason 篩，誤判出 586 條，改用 hint 內容
判斷後才收斂到 21 條。

另外兩條是人工查證發現的：

```
"高速公路":   "復興路"    ← 會讓國道案件被判成一般門牌地址，走錯處理分支
"新北大道路": "思源路"    ← 疑似目標寫錯，應為「新北大道」
                            （來源多一個「路」字，原意應是修正 STT 的「新北大道路」）
```

### `map_city.json` 同一個病（7 條）

```
中正區 → 中和區    萬華區 → 中和區    北投區 → 板橋區    士林區 → 樹林區
新屋區 → 新莊區    桃園區 → 泰山區    蘆竹區 → 蘆洲區
```

臺北市士林區的報案會被改成新北市樹林區。

## 問題二：沒有相似度下限

抽樣 3000 條計算來源與目標的臺語相似度（用貴方提供的 `ese.py`）：

| 相似度 | 佔比 |
|---|---|
| ≥ 0.8 | 約 38% |
| 0.5 – 0.8 | 約 37% |
| **< 0.5** | **約 25%** |

最低的幾條：

```
0.077  昇華路 → 自立街     siann-hôa-lōo / tsū-li̍p-kai
0.083  蘆洲路 → 鷺江街     lôo-tsiu-lōo  / kang-kai
0.100  老安路 → 八德街     lāo-an-lōo    / pê-tik-kai
0.125  客運頭街 → 車路     kheh-ūn-thâu-kai / tshia-lōo
```

臺語拼音完全不像。（部分看起來像「地名別稱」而非音近，可能混了另一個來源，
但沒有生成腳本無法確認。）

同樣的問題也出現在 `address_mapper_119._fuzzy_match_district_by_tl()`：
`best_score` 從 **-1.0** 起跳、取最高分，**任何輸入都必定回傳某一區**。
實測「不分區」→「瑞芳區」（0.583）、「沒有區」→「八里區」（0.444）。

## 問題三：1934 個來源是其他來源的子字串

`_apply_simple_mapping` 用 regex 一次替換所有匹配，來源互相包含時會疊加替換。
上述真實通話的 `新新新新新新思源路` 即由此而來。

---

## 建議

1. **生成時排除「變體本身已是清單中的真實路名」**——這是最重要的一項。
   可用 addrCheck 驗證，但**判準要看 hint 內容而非 reason**（見上方說明）
2. **設相似度下限**（`map_street.json` 與 `_fuzzy_match_district_by_tl` 皆需要）。
   參考：真實 STT 錯誤「汐只區→汐止區」為 0.636，而合法區名誤配「文山區→金山區」
   高達 0.769——**單靠門檻不足以區分，仍需第 1 項的白名單過濾**
3. **檢查來源之間的子字串包含關係**，避免疊加替換
4. 修正 `"新北大道路": "思源路"`（目標疑似寫錯）
5. **評估這張表是否仍必要**：addrCheck 本身已內建同音修正，且更保守——

   ```
   「重陽路1號」查無此路名，已依讀音修正為「新北市蘆洲區中央路1號」
   （本轄同音路名僅此一條）。注意：兩者讀音相同，向報案人…
   ```

   它只在「本轄同音路名僅此一條」時才修，且會回傳明確說明。本地表在許多情況下
   是重複且更危險的一層。

## 我方目前的處理（暫時性）

在不修改貴方資料表的前提下，於 119 端做了兩層防護：

1. **街路映射延後**：先拿報案人原話問 addrCheck，**查得到就不套映射表**，
   查無才啟用。報案人講對的路名不再有機會被改掉
2. **排除清單** `scripts/map_street_exclude.json`：載入時濾掉 **3081 條（12.1%）**，
   剩 22358 條有效映射。判準有二：來源本身是真實路名（21 條）、
   臺語相似度 <0.50（3067 條），另加人工判讀 2 條。獨立成檔，
   貴方更新 `map_street.json` 不受影響

   我方的立場是「寧可少映射」——查無時 addrCheck 的 hint 會針對報案人的原話
   給建議（「查無『桃園街』，是否為公園街？」），比套用一條不確定的映射安全。
   日後真實通話出現某個 STT 錯法而該映射剛好被排除，再逐條加回。

驗證工具：`scripts/audit_street_mapping.py`（逐條打 addrCheck 檢查來源是否為真實路名），
輸出 `scripts/map_street_audit.json` 可直接參考。

226 通真實通話離線重放：改善 17 通、回歸 3 通（均已查明非本次改動所致）。

補充：另做過一組對照實驗——排除清單套用後，「先套表」與「查無才套表」兩種順序
的提問趟數差 0.004 句/通（226 通中 225 通完全持平）。**修正表的內容才是關鍵，
套用時機的影響可忽略**。
