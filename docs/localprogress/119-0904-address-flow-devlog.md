### 階段 1：地址驗證（修法 1 + 3）

**先排除 API 的嫌疑**——直接打 addrCheck：

```
土城區中央路3段61巷2號   → status:true  ← 報案人第一次講的地址本來就有效
土城區中央路3段二十六11巷2號 → not_found
板橋區大華街2號          → road_only「鄰近門牌為 1號、5號、7號」
```

API 完全正常、回應快、判斷正確，還附上可直接拿來問的建議。問題在我方。

**根因**：`_DISTRICT_RE` 的 `[一-鿿]{1,4}區` 貪婪往前吃：

```
「欸我住在那個辦土城區中央路3段61巷2號4樓」
        └──────┘
   district = 「個辦土城區」   →  組出「個辦土城區中央路…」→ API 必然查無
```

**修法**：
- `_KNOWN_DISTRICTS` 白名單（新北29＋北市12＋基隆4＋桃園13），取「區」字前最長合法區名
- ⚠️ 光把 `{1,4}` 縮成 `{2,3}` 沒用——「辦土城區」照樣中，必須用名單
- 引擎失敗訊息改吃 API 的 `reason`（`road_only`→查無此門牌、`not_found`→查無此路段），取代寫死的「地址查無管轄單位」（那是 jurisdiction 年代的遺留，119 早就不查分局）

### 階段 3：孕婦急產案，派遣地址被產檢醫院蓋掉（09-04 09:45）

三胞胎 32 週羊水破裂，救護車 09:43:36 已派出。09:44:36 AI 問「在哪裡產檢？」，
報案人答「國泰醫院」——`case.address` 當場被覆寫成醫院名。

```
address       = 國泰醫院        ← 派遣看這個
address_road  = 那個亞洲路      ← 真正的事發地還在元件欄位
```

**根因**：`_apply_location_rules()` 每輪都跑，判到地標/捷運/路口就**無條件覆寫**
`case.address`，不看地址是否已成立、是否已派遣。`classify_location_type("國泰醫院")`
靠「醫院」二字即判 landmark（地標名單其實是空的，不需名單）。

對照組：另一條路徑 `_apply_extracted_fields` 有 `merge_address` 保護，實測會保留原址。
就這條規則路徑沒有任何守衛。

**修法**：`_address_locked`——`_run_address_flow` 用 `try/finally` 包住內層（內層有
5 個提前 return，只有 finally 涵蓋得完），流程結束即上鎖；上鎖後不再覆寫已成立的地點。

⚠️ 守衛條件不可改用 `address_confirmed` / `validation_status=="valid"`：出事那通
兩者分別是 `False` / `invalid`，擋不住。

### 階段 4：STT 誤聽與「不能隨意影響判斷」

同通還有「不分區」被當成行政區（regex 退路匹配到），組出「不分區亞洲路3號」。

加了 `_NON_DISTRICT_WORDS` 濾除後，發現更嚴重的事——**`address_mapper` 的臺語音近
比對沒有門檻**：`best_score` 從 -1.0 起跳、取最高分，**任何輸入都必定回傳某一區**。

```
不分區 → 瑞芳區 0.583     沒有區 → 八里區 0.444     不知道 → 蘆洲區 0.333
```

我一度想用門檻解決，被指出「**雖然我知道實際是土城區但這不能隨意影響判斷吧**」——
用已知答案挑門檻本身就是錯的方法。改成三層處置：

1. `map_location_detail()` 回報哪些是猜的（走回傳值不走實例狀態——mapper 是進程內單例）
2. 猜出來的區**必須覆誦確認**，話術把區單獨點出來讓報案人有機會否認
3. 沒走完覆誦就失敗時，`_revert_unconfirmed_district_guess()` 把猜測**還原成原文**，
   不把未確認的猜測留給接手的真人

### 階段 5：五步地址流程（依規格實作）

規格（使用者提供）：歷史補抽 → 缺什麼問什麼（模糊猜測先核對）→ API 驗證＋hint 導向
→ 引導式逐級 → 回報受理員。

先蒐集 addrCheck 的 hint 真實格式，發現**五種**，而且 `road_only` 涵蓋三種不同情況：

| hint | 該問什麼 |
|---|---|
| 查無此門牌；同路段鄰近門牌為 1號、5號、7號 | 門牌號錯 |
| 「土城區中央路」分成 一段、二段、三段、四段 | **缺段** |
| 已確認路名「板橋區大華街」，請追問門牌號碼 | **缺號** |
| 查無「中央路三段二十六」，是否為 新北市土城區中央路？ | 路名錯，有建議 |
| 查無「不存在路」這條路 | 路名錯，無建議 |

**光看 `reason` 不夠，必須解析 hint。** 後兩種是我原本沒想到的——API 直接告訴我們
該問什麼，比自己猜準。

實作成獨立檔 `address_hint_119.py`（換版整檔複製，不必逐行 port），解析失敗一律
退回泛用問句，不讓 API 改文案就弄壞整條流程。

### 階段 6：地標模糊比對（從「既有測試失敗」挖出來）

檢視那 6 項既有測試失敗時，發現其中兩項不是「測試過時」而是**真缺陷**：

```
捷運頂埔站出口1   → 捷運新埔站（完全不同的站）        status=true
捷運不存在站出口9 → 捷運亞東醫院站2號出口              status=true
未知市場旁邊      → 市場 → 文山區景隆街2號附近（跨北市）status=true
```

addrCheck 的地標比對**同樣沒有相似度門檻**，只要含「市場」「捷運」「站」就硬配一個
最相近的。而 API 自己的 hint 就寫著「若不確定請向報案人確認是否為此處」——我們卻
直接把 `status=true` 當通過。

這是 **API 端**的問題，我們改不了，只能在流程上要求確認。

### 階段 10：上線第二批四通（20:55–21:06）

一通完美（21:06 汐止區福德路，一次就過、valid、confirmed），另外三通抓到：

**① 「API 查無」與「報案人沒確認」被混為一談（20:55）**

那通地址其實是對的——`reason` 裡就寫著「系統提示：**地址有效**：新北市三重區
仁愛街283巷28號」，卻標成 `invalid` + `地址搜尋失敗`，受理員會誤以為查不到地址。

根因：`_mark_address_failure` 無條件把 `address_validation_status` 覆蓋成 `invalid`。
但那是 API 判定，跟「報案人有沒有明確確認」是兩回事。

修法：API 已驗證通過時不覆蓋狀態，標籤改用新增的 **「地址未確認」**；
真的查無才標「地址搜尋失敗」。

**② `map_street.json` 的錯誤映射（20:57，派遣地址完全錯誤）**

報案人講「重陽路跟新北大道的岔路交叉路口」，存檔地址是
`板橋區三和路與新新新新新新思源路口`，而且 `result=dispatched`。

```
重陽路      → 三和路       ← 三重區重陽路是真實存在的路（API 回 ambiguous，有一/二/四段）
新北大道路  → 思源路       ← 報案人的「新北大道」＋後面的「路」被連著吃掉
```

`map_street.json` 有 25439 條，其中 **1934 個 key 是別的 key 的子字串**，
會造成部分替換疊加（「新新新新新新」的來源）。**0903 行為相同**，是既有的資料品質問題。

⚠️ **未修**：這是使用者維護的資料表，且要治本得改流程順序（先用原文查 API，
查不到才套映射），風險大。已記錄待決。

**③ 第六種 hint：`ambiguous`（查證 ② 時發現）**

```
三重區重陽路1號 → [ambiguous]「重陽路」的 一段、二段、四段 都有 1 號，
                              是不同的地點，請追問報案人是哪一段。
```

同一門牌號在多個路段都存在，不追問就會派到錯的段。原本解析器沒這條，
會退回泛用問句。已補：解析成 `need_section`，問「重陽路有分一段、二段、四段，
請問是哪一段？」

**④ 巷弄在 hint 重問時丟失（20:55、21:02 各一次）**

報案人講「仁愛路283巷28號」，hint 導向把路名改對成「仁愛街」後，**283巷 不見了**，
覆誦時唸成「仁愛街28號」，報案人連續否認兩次。`_HINT_CLEAR_FIELDS` 清掉
`address_road` 時，巷的資訊一起沒了。⚠️ **未修**，需要讓巷弄獨立於路名保存。

### 階段 11：map_street.json 全表驗證（09-05）

20:57 那通派錯地址後追查 `map_street.json`，過程本身就是一次教訓。

**第一次抽樣（600 條結構可疑的）→ 報 23 條有問題。**
**全表 25439 條跑完 → 先報 586 條，抽樣一看發現判斷邏輯根本是錯的 → 實際是 21 條。**

錯在哪：我拿 API 的 `reason` 當判準，`EXISTS_REASONS = {valid, ambiguous, road_only}`。
但 addrCheck 的語意不是這樣：

```
"中小街" → "忠孝街"   [ambiguous]
    「中小街1號」查無此路。同音的「忠孝街」在 三峽區…都有
         ↑ ambiguous 指「你講的查無，但同音的有好幾條」，中小街並不存在

"加新村街" → "新春街"  [valid]
    地址有效：新北市金山區金包里街1號
         ↑ valid 也可能是 API 模糊比對到完全不同的路
```

正確判準是**「API 回傳的地址裡有沒有原路名」**。改用 hint 內容判斷（不必重打 API，
hint 都在結果檔裡），586 → 21。抽驗 7 條全部正確。

最終結果：

| | 條數 | 佔比 |
|---|---|---|
| 來源本身是真實路名 | 21 | 0.08% |
| 映射合理 | 25416 | 99.9% |
| 無法判定 | 2 | — |

**表的整體品質其實很好**，我先前基於錯誤數據把問題講得太嚴重。

同一階段還做了一組乾淨的對照實驗（使用者指出前一版比較混淆了變因）：
**排除清單套用後**，「先套表」vs「查無才套表」的提問趟數差 **0.004 句/通**，
226 通中 225 通完全持平。**修表才是關鍵，順序的影響可忽略。**

### 階段 16：方向修正——從「加 regex 規則」轉為「讓 LLM 讀整段對話」（09-06）

第五批四通後，使用者提出三點，第三點是方向性的質疑：

而 summary 的 LLM 看得到整段對話，自然理解「4號9樓」才是門牌。這不是 prompt
不好——`extract_address` 的 prompt 寫得相當細——是**餵給它的資訊不夠**。

離線評測（`scripts/eval_consolidate_address.py`，14 通有人工正解）：

| | 命中 |
|---|---|
| 規則抽取 | **5/14** |
| `consolidate_address`（吃全部發話）| **13/14** |

規則錯的全是同一類，而且**正是這幾天一條條加規則在修的東西**：

```
國光路11號    缺 31巷        仁愛路283巷      STT 未修正
景平路27號    缺 431巷       帶進路1段5551號  STT 未修正
```

使用者的判斷成立：**靠實際測試一條條調 regex 是打地鼠**。架構調整為

| 層 | 負責 | 狀態 |
|---|---|---|
| 理解 | 從多輪對話整合地址、識別口誤與補述 | ✅ `consolidate_address` |
| 解析 | 地址字串 → 區/路/號元件 | regex（堪用） |

```

        地址錯了卻沒有任何警訊
```

### 階段 17：第六批五通——裸區名、日期、假派遣（09-06 04:41–04:47）

第一批**在 LLM 整合上線後**（服務 04:36 重啟）測的通話。五通裡兩通是同一個開場：

```
報　救護車在那個。鶯歌那邊。
AI　確定是鶯歌這個地址嗎？        ← 走到地標分支
```

`extract_address_district` 只認得帶「區」的寫法，「鶯歌」抽不到 → 判成地標。
口語省略「區」是極常見的講法，卻一直沒被真實通話打到，是因為前幾批的報案人
剛好都講了「區」或直接講路名。

補上 `_bare_district()` 後最需要小心的是**別把路名前綴當成區**。做法是前後
都要有線索，而且**只收新北市 29 區**：

```
中山北路二段100號   ← 若收臺北市區名，會拆成「中山區」＋「北路」（＝⑩-6 那個坑）
我要送台大金山。開刀  ← 「金山」前面是「大」，不在前置線索名單 → 不認
中和路100號         ← 後面只有「路」字，regex 要求路名有前綴字 → 不認
這是三重點          ← 後面是「點」 → 不認
```

第四通被 BERT 判成救護（句子裡有「叫救護車」），**整通的軌跡是分類錯誤造成的，
不是地址流程的參考值**——分類是 BERT 的範圍，不在本版調整範圍內，所以這通
不進 fixture。但它順帶暴露了兩個與分類無關的通用缺陷，這兩個留下來修：

**一、「號」同時是門牌與日期的量詞。** 報案人交代病史或事發時間會講裸的
「N號」（「他3月23號開過刀」「上禮拜5號就這樣了」），`extract_address_number`
取第一個匹配就把日期填成門牌。改成跳過前面是年／月／日的匹配繼續往後找，
所以「3月23號那次是在中央路3段61巷2號」仍抽得到 2號。

**二、OHCA 轉真人的話術寫死「救護車已派出」。** 生命征象是在地址流程**之後**
才問的，任何在派遣前就轉出去的通話——地址查不到、報案人講不清楚、打錯電話——
都會聽到這句不實陳述。改成看 `_dispatch_announced`，只有真的講過派遣句才保留
前半句。

順手把第二輪重問改成只問缺的元件。修完這兩通的軌跡：

```
修正前  地址？ → 確定是鶯歌這個地址嗎？ → 請問是哪一區？ → 覆誦   （4 句）
修正後  地址？ → 鶯歌區的哪一條路呢？ → 覆誦                （3 句）
```

**收案原則**：因分類錯誤而走偏的通話不進 fixture、也不拿來調規則——那通的
提問順序反映的是 BERT 判錯，不是地址流程的問題，收進去只會把噪音鎖進測試。
它暴露的**通用**缺陷（上面那兩個）仍然照修，測試改用中性的合成字串。

**回歸檢查**：把新規則關掉當對照組，掃 408 通 1628 句報案人發話——
行為改變 12 句，11 句是正確補上區名（土城／板橋×3／新莊×2／中和／鶯歌×3），
1 句是那個日期。**沒有任何一句的區名被改掉或門牌被改錯。**

fixture 隨之更新：三句舊期望值（「板橋國光路」「中和景平路」「新莊。區中港路」）
原本寫 `expect_district=None`，那是**當時抽不到**，不是人工判讀的正解。裸區名
生效後改回應有的區名——這批正是 ⑩-13／⑩-14 繞遠路的那幾通。

### 階段 18：第七批四通——沒有切點的句子（09-06 10:35–10:42）

四通裡三通一問一答就派遣完成（五股六合街兩通、新店中興路三段），
裸區名與缺項重問都照預期運作。第一通有問題：

```
報　是。200之1號8樓。
AI　請問是什麼路？          ← 路名早就講過了，倒退問
```

`extract_address_road` 的切點只有「區」和縣市。這句兩個都沒有，於是從句首
開始比對，抽出「我這邊是民生路2段」，含「我」「是」被 `looks_like_real_road`

第一版修法是逐字往右剝到不含敘述詞為止，馬上被真實語料打臉：

```
我不知道什麼路欸      → 「道什麼路」   ✗ 比 None 還糟
我看到有人在光復路    → 「到有人在光復路」 ✗
他就在馬路旁邊        → 「馬路」        ✗
我是路人路過現場      → 「路人路」      ✗（fixture 明定這句不得抽出地址）
```

改成**只剝口語贅詞用字**（`_ROAD_FILLER_CHARS`），並補三個判準：疑問詞與
「路人」列入拒絕清單、「馬路／路口」等通稱只擋完全相等、路名主體全由贅詞字
組成時不算路名（擋「那個路」）。

那張贅詞字表**刻意不收任何可能當路名開頭的字**，這是不會剝成「北路」的保證：

```
中山北路二段   中 不在表內 → 一個字都不剝
我這邊是民生路2段  我這邊是 全在表內 → 民生路2段
躺在中山北路二段   躺 不在表內 → 停 → 含「躺」→ None（維持原行為）
```

408 通 1659 句 A/B：10 句由 None 變成正確路名，**0 句回歸**。

**這個修正打開了一個既有漏洞。** 修完 `test_llm_result_rejected_when_api_invalid`
失敗了——那條測試用假路名「不存在路」驗證「LLM 判讀沒通過 addrCheck 就不採用」。
查下去發現閘門本身是對的（`result.valid is not True` 就 return False），
但候選在**送驗之前**就記進 `_address_candidates`，而最後的
`_restore_best_candidate()` 挑選只比「哪個字多」——LLM 整合出來的地址往往最長，
於是被 API 否決的地址又被撿回來寫進 `case.address`。

這條測試一直是**巧合**通過的：「不存在路」含「不」，被路名 regex 擋掉，
根本走不到記錄候選那一步。贅詞剝除讓它走到了，漏洞才現形。加上
`_API_REJECTED_REASONS` 過濾；`api_status` 為 `None`（還沒驗過）不算否決，
09-02 那通還原第一次講的有效地址仍要靠這條路徑。

### 階段 19：分類與驗證的分工（09-07）

第七批之後回頭追一個問題：報案人說「我想要到那個亞東醫院」，為什麼沒被當成
地標？查下去發現**本地地標表是空的**：

```
MRTstation.csv  → 506 筆   ✓ 所以捷運判得準
landmarks.xlsx  → 0 筆     ✗ 只有標題列
```

`classify_location_type()` 有一支 `if any(name in s for name in landmark_names)`，
名單永遠是空的，**從來沒有觸發過**。地標全靠下一行 `_is_landmark_only()`
那 19 個關鍵字硬撐。同一段程式碼、兩種命運。

而驗證那一層早就不看本地表了——`validate_landmark()` 的 docstring 寫著
「path 參數保留相容」，實際走 addrCheck `type=Landmark`。五種型態全部
走同一支 API，靠 `type` 分流：

```
address → House    intersection → Crossroad    highway → Freeway
landmark → Landmark    mrt → Landmark
```

順著查下去發現關鍵事實：**分類判不出來時預設 `address`，是在傷害自己**。

```
板橋國小   House → 查無「國小」        Auto → 文化路一段23號
南山高中   House → 是否為南山路？      Auto → 中和區南山高中
陸光新城   House → not_found          Auto → not_found（一致）
```

House 層會把「板橋國小」切成「國小」去找路名。而 Auto 一個都沒錯。
API 自己也在提示：「指定 type=House，但文字中找不到路名，請改用 Auto」。

所以做了兩件（使用者的話：「先做一和二試試看，不行的話再回原來規則」）：
**判不出來就別猜，交給 addrCheck 自己判**；**純區名／縣市名不送驗**——
後者是前者的前提，因為自動層對「五股區」會回 valid 並配到五股區公所、
「新北市」配到樹林區肉品市場。

**但 ① 一開始完全沒有用**，因為映射在探測**之前**就把名字改壞了：

```
板橋國小 → 板橋插角國小        map_other_road.json: "國小" → "插角國小"
新北大道 → 新新北大道          "北大道" → "新北大道"
台灣大道 → 台灣縣民大道        "大道" → "縣民大道"
```

「新新北大道」正是 vendor 報告裡那通火警（09-04 20:57 存成
「三和路與新新新新新新思源路口」）的同一個病，這次從另一張表冒出來。

判準分兩類：通用名詞當鍵 → 排除清單；**目標名稱已在原文裡就不替換** →
通則，一次擋掉 15 筆「鍵是自己值的子字串」的條目。

1659 句 A/B：映射結果改變 6 句，**全部是修好原本被改壞的文字，0 回歸**。

留下的判斷：**不補 `landmarks.xlsx`、不補關鍵字表**。驗證早就不看本地表，
①落地後關鍵字表只剩流程分支的用途（要不要問樓層、要不要追問第二條路），
判不準不再是安全問題。補表反而會重演 map_street 的老路——本地資料跟
addrCheck 打架。

### 階段 20：第八批四通——覆誦唸對的，存檔存錯的（09-07 17:01–17:12）

三通乾淨（樹林和平街、三重安慶街、板橋合安一路），一通有真 bug。

板橋合安一路那通值得單獨說：STT 嚴重劣化，「請問是幾號？」問了三次。
但我查過報案人講的四個版本，`175巷` 在合安路、合安一路、合宜路上**都不存在**，
API 只能確認到路名——**這通沒有正解**。系統判 invalid、標記
`address_suspect_error`、把報案人講過的所有版本附給受理員、照樣派遣。
這正是第五步的設計行為，不是 bug。

真正的問題在 17:04：

```
報　地址在那個新北市永和區永鎮路128號。
        addrCheck：「永鎮路128號」查無此路名，已依讀音修正為「永貞路128號」
AI　確定是新北市永和區永貞路128號這個地址嗎？      ← 唸的是修正後的
報　對。是的。
存檔 → 新北市永和區永鎮路128號                     ← 存的是修正前的
```

`display_address()` 只是回傳 `case.address`，所以覆誦當下它**確實是**永貞路。
之後被逐輪 LLM 從原話再抽一次蓋回去：

```
merge("…永貞路128號", "…永鎮路128號") → "…永鎮路128號"
```

**派遣資料存了一條不存在的路，而 `address_validation_status` 還是 `valid`**
——驗證是在被蓋掉之前做的。

修法是寫入前問「是不是同一個地方的另一種講法」：拿映射表正規化新地址，
等於現在這個就跳過。映射表本來就知道永鎮路→永貞路，而報案人真的改地址時
兩者不會相等。

修完才發現第二層：`address_road` 還停在「永鎮路」。`_fill_components_from_address`
是「已有值不動」——這對逐輪累積是對的，但地址被整個換掉之後，舊元件是舊地址
的殘骸。加了 `overwrite=True`。

最後照 API 自己的警告加了標記。它的 hint 後半句寫著：

> 注意：兩者讀音相同，向報案人複述路名無法分辨，如需確認請改問門牌號、
> 樓層或附近路口。

也就是說 AI 唸「永貞路」、報案人答「對」，**那個「對」不具鑑別力**。
新增 `address_corrected_note` 欄位給前端。**不攔流程**——API 只在
「本轄同音路名僅此一條」時才修，沒有第二個候選會弄錯，不值得為它多問一輪。

## 二、修過頭又收回的紀錄 ⚠️

### 保留路名前綴，卻用了會切掉「段」的函式（09-06）

`merge_address` 補述吃掉路名，修法是把前綴保留到路名為止。第一版用現成的
`_extract_road_core(cur)`，測試立刻紅：

```
期望  新北市板橋區民生路二段200之1號8樓
實得  新北市板橋區民生路200之1號8樓        ← 「二段」不見了
```

`_extract_road_core` 回的是「民生路」，段／巷／弄都被切掉——它本來就是拿來
比對「是不是同一條路」的，不是拿來當前綴。改用 `extract_address_road()`。

**修 A 的時候順手拿了個名字很像的函式，就換成 B 壞掉。** 這類錯誤靠讀程式
碼很難發現，靠一條寫死期望值的測試三秒鐘就抓到。

### 排除通用映射鍵，第一版判準會誤殺合法補全（09-07）

`"國小"→"插角國小"` 這類條目的共同特徵看起來是「鍵是自己值的子字串」，
表上有 15 筆。但直接照這個判準排除會誤殺：

```
"冷飯" → "冷飯坑"     報案人講「冷飯」，真實地名是「冷飯坑」——這是合法補全
"破布子" → "破布子腳"
```

真正的區別是**輸入是否已經是正確的完整名稱**。所以拆成兩條規則：通用名詞
（國小／大道／社區）進排除清單；「目標名稱已在原文裡就不替換」當通則。
後者讓「冷飯」仍會補成「冷飯坑」，而「冷飯坑」不會變成「冷飯坑坑」。

### 逐字剝贅詞，剝出比 None 更糟的東西（09-06）

「我這邊是民生路2段」抽不到路名，第一版修法是從左邊逐字剝、剝到不含敘述詞
就停。單看那一句是對的，拿 1659 句真實語料一跑，四個誤抽全是憑空生出來的
路名（「道什麼路」「路人路」「馬路」「到有人在光復路」）——其中「我是路人
路過現場」還是 fixture 裡明定不得抽出地址的敘述句。

**抽錯比抽不到糟**：None 會讓流程去問，錯的路名會被拿去查 addrCheck、
被覆誦給報案人。改成只剝白名單內的贅詞字，寧可停在原地。

### 既有測試的斷言被新行為推翻，不能直接改成「現在的樣子」（09-06）

`test_stripping_never_produces_invalid_road` 斷言「那個路口」要抽出
`len > 1` 的路名，本意是防止剝到只剩「路」。新判準讓它回 None，測試失敗。

直接把斷言改成 `assertIsNone` 就會把原本的保護（不得剝出單一通稱）弄丟。
改成同時斷言兩件事：不得是「路／街／大道」，且若非 None 則長度 > 1。

### 期望值改在產出物上，被下一次重建蓋掉（09-06）

裸區名上線後 fixture 三句失敗，我直接改了 `tests/data/real_calls_119.json`，
測試轉綠。跑 `build_real_call_fixture.py` 加新通話時整份重建，三句又變回
`None`，失敗重現。

期望值的來源是 `scripts/build_real_call_fixture.py` 裡的 `EXPECTED`，
JSON 只是產出物。**改產出物等於沒改。**

**這節是本文件的重點**——這些是「改了以為變好、實際弄壞別的」的案例。

### 1. 剝區名簡稱，把正確路名削壞

為了處理「三重正義南路」（報案人只講「三重」不講「三重區」），我把區名的簡稱
也加進路名前綴剝除清單。結果：

```
中山北路二段  →  北路二段     ← 「中山」被當成中山區的簡稱剝掉
```

而「北路二段」照樣 `fullmatch` 成合法路名，原本的守衛擋不住。**測試抓到**。

**收回**：只剝完整區名，不剝簡稱。簡稱與路名無法從結構區分——「三重正義南路」的
「三重」該剝、「中山北路二段」的「中山」不能剝。少剝一個交給 API hint 導向修正，
好過把正確路名剝壞。

### 2. 「不是明確否認就當確認」

為了不讓急案為措辭多耗一輪，我把猜測的確認寫成「不是明確否認就視為確認」。
`parse_yes_no("不知道")` 回 `None` → 報案人一句「不知道」，系統就把猜測當事實採用。
**離線重放抓到**（回答用盡後補「不知道」，模糊比對的地標全被當成確認）。

**收回**：`is_uncertain_answer()`，不知道／不清楚／不確定／沒印象一律視同未確認。

### 3. 用已知答案挑門檻

音近比對加門檻時，我拿「土成區→土城區 0.800」當依據挑了 0.6。被指出這是用已知
答案反推參數。而且後來證明**門檻方法本身就不夠**：文山區→金山區 0.769 比真實
STT 錯誤汐只區→汐止區 0.636 還高。

**收回**：改成「已經是合法行政區名的，根本不拿去猜」，門檻降為第二道防線。

### 4. 改用 `verify_address_detail` 破壞一批測試 mock

五步流程實作時我改用 `verify_address_detail()`，結果 13 個測試失敗。檢查後發現
`query_jurisdiction` 回的 `JurisdictionResult` **本來就帶 `api_reason` 和 `error`(hint)**，
資訊完全一樣。

**收回**：改回 `query_jurisdiction`，少破壞一批 mock 點。

### 5. 引導式清了元件卻沒清 address，等於沒作用

第四步引導式清空區/路/號後準備逐級重問，但沒清 `case.address` →
`_fill_components_from_address()` 立刻從舊地址把元件補回來。問句序列直接從
「我們一項一項來，請問是哪一區？」跳到「請問是幾樓？」。

**收回**：連 `case.address` 一起清；失敗時再用 `_restore_address()` 還原，
別讓受理員接到一片空白。

### 6. 五步疊起來提問次數會爆掉

第二步 6 次 ＋ 第三步 12 次 ＋ 第四步 5 次 ≈ **20+ 次提問**。急案不能這樣拖。

**補救**：`_ADDRESS_ASK_BUDGET = 10`，所有地址提問走 `_address_ask()`，
用完直接收斂到第五步。

### 7. 測試污染正式取樣檔

模糊比對取樣預設寫 `{LOG_DIR}/fuzzy_matches.jsonl`，跑測試就把測試資料混進正式樣本——
而那份樣本是要拿來調 API 門檻的。試過 `tests/__init__.py` 和 `discover -t .` 都無效
（discover 以 top-level 名稱載入模組）。

**收回**：改設計本身——**沒設 `LOG_DIR` 或 `FUZZY_LOG_PATH` 就不寫**。service 有設
`LOG_DIR`，正式環境照常取樣；測試環境沒有，自然停用。

### 8. fixture 第一版記錄「完整流程狀態」，測出假回歸

第一版 fixture 記錄每通的最終 status。結果 19:54 那通測出 invalid——真正原因是
問句改變後，報案人原本回答「哪一區」的那句被拿去當覆誦的回答。

**收回**：只記**不受問句影響**的東西（原話→元件、地址→API 判定），流程層只斷言
不崩／不超預算／已鎖地址不被改寫。

### 9. 重複計數污染統計

模糊比對取樣時，「否認 → 還原」會記兩筆（denied + unconfirmed），統計失真。

**補救**：`_district_guess_sampled` 旗標，同一次猜測只取樣一次。

### 10. 差點踩 VRAM 雙開雷

驗證時直接 `import sop_api_server`，**沒帶降級三件組**，它 module-level 就載 gguf 和
BERT（輸出有「子分類器就緒」）。線上服務當時佔 24GB/32GB。運氣好沒 OOM。

**教訓**：任何 import `sop_api_server` 的驗證都要先給
`GGUF_MODEL_PATH=/nonexistent` + `ENABLE_MAIN_CLASSIFIER=0` + `ENABLE_SUB_CLASSIFIER=0`。

### 11-b. 「目標不存在」整層判準不可靠

三層過濾的第二層用「不帶行政區查 addrCheck」判斷映射目標是否存在，報出 246 個
目標、537 條映射。使用者一看清單就指出汐科路、漁澳路、擺街堡路等**實際存在**。
查證後確認：不帶區查詢對很多路名查不到；擺街堡路、桀魚坑路 API 其實用讀音修正
找得到，只是我的判準沒接住。

**收回**：整層廢棄，改用 L1（來源是真實路名）＋ L3（相似度過低）。
**教訓：驗證方法本身也需要驗證——在地知識比自動化查詢可靠。**

### 11. 拿 API 的 `reason` 當存在性判準，誤判 28 倍

全表 audit 第一版用 `reason in {valid, ambiguous, road_only}` 判斷「來源路名是否存在」，
報出 586 條問題。抽樣 18 條一看，大部分是誤判——`ambiguous` 的語意是「你講的查無，
但同音的有好幾條」，`valid` 也可能是模糊比對到別條路。改看 hint 內容後收斂到 21 條。

**收回**：`road_exists(key, hint)` 改判「API 回傳的地址裡有沒有原路名」，
並在腳本裡把這個陷阱寫成註解。**教訓：API 的 reason 是給流程分支用的，
不是給語意判斷用的；要判斷語意就得看 hint。**

### 12. 對照實驗混淆變因

比較「街路映射延後」的效果時，兩組都跑在**含錯誤條目的表**上，於是測出
「延後讓提問從 4.30 降到 4.07」。但那個好處其實來自「延後避開了表的錯誤」，
不是順序本身。使用者指出後重做對照（兩組都套排除清單），差距是 0.004 句/通。

**收回**：結論從「延後能減少問話」改成「延後的價值是保護未驗證的條目；
修表才是關鍵」。並加了 `STREET_MAPPING_MODE` env 讓順序可切換。

### 13. 重放腳本把輸出寫進版本目錄

`replay.py` 內有 `os.chdir(VERSION_DIR)`，之後的相對路徑輸出就寫到 0903／0904
目錄裡了。已移出並確認版本目錄乾淨。

## 三、驗證方法的演進

三種方法能證明的事不同，**缺一不可**：

| 方法 | 能證明 | 證明不了 |
|---|---|---|
| 單元測試（231 項）| 邏輯正確、邊界處理 | 真實輸入長什麼樣 |
| 離線重放（226 通）| 不崩、不回歸、提問不失控 | hint 導向的效果（沒有真人回答）|
| 真實通話上線 | 全部 | —（但一次只有幾通）|

**沒有 LLM 的盲區**：地址測試幾乎都不帶 `llm_extractor`，`self._llm is None` 時
engine 裡十處 LLM 分支全部跳過。線上 `llm_loaded=true`，跑的是沒測到的那一半。
後來補了 `StubLLM` 覆蓋主要分支，但真實 LLM 會抽出什麼，只有真通話跑得出來。

**離線重放的用法**（切 systemd 前的低風險驗證）：

```bash
# 對兩個版本各跑一次，比對狀態變化／例外／提問次數／地址資訊增減
ADDRCHECK_API_URL=… ADDRCHECK_API_TOKEN=… FUZZY_LOG_PATH=/tmp/x.jsonl \
  python replay.py <版本目錄> <輸出.json> all 226
```

⚠️ 統計時要排除**非新北市的門牌地址**（恆為查無，會低估通過率），但
**地標／國道／捷運／路口一律保留**——那些型態不受縣市限制，且引擎分支不同，必須驗證。
226 通樣本中符合排除條件的只有 2 通。
