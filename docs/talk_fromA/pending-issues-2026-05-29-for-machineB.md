## Issue #1：Whisper STT 的 stop → FINAL 延遲過長

### 觀察日

2026-05-28（切換到 Whisper Adapter `ws://192.168.5.204:8891/SttProxy/recognition` 後）

### 現象

機器A 端的 VAD 偵測到 800ms 靜音後，主動送 `stop` 給 STT server，**預期立即拿到 FINAL** 結果，但實際上 FINAL **延遲過久**（體感「非常久」），導致使用者「說完到聽到 AI 回覆」的整體延遲顯著高於可接受範圍。

### 對比 Cyberon（之前 backend）

| 項目 | Cyberon | Whisper Adapter |
|------|---------|-----------------|
| `do_epd=True` 模式 | 串流：邊收音邊辨識，stop 後幾乎立即回 FINAL（< 0.3s） | **未實作 server-side EPD**（依文件說明），stop 後才整批處理 |
| 端對端體感延遲 | 說完話 → 聽到回覆約 3–4 秒（可接受） | 說完話 → 聽到回覆顯著拉長 |

### 推測原因

Whisper 為 batch 推論（非串流），`stop` 之後 server 才把累積的整段音訊一次送進模型；音訊愈長等愈久。
官方文件提供的數據：50 秒音訊約 11 秒推論（RTF 0.22x），雖然標稱「real-time 場景沒問題」，但實際電話對話場景的單句也可能達 3–5 秒，stop 後再等 1–2 秒回 FINAL，整體延遲就超出可接受範圍。

### 機器A 側已採取的措施

- 客戶端 VAD（Silero）已負責端點偵測與主動 stop
- VAD 靜音閾值已調為 800ms（平衡準確度與延遲）
- 收 partial 流程已不依賴，只用 FINAL 累積

→ 機器A 側無進一步可優化空間，延遲瓶頸在 server 端。

### 期望機器B 回覆

1. Whisper backend 是否可改為串流推論（chunked inference）？或部分串流？
2. 如不行，是否有其他可降低 stop → FINAL 延遲的方式？
   - 例：使用更小的 Whisper 模型（small / base 而非 large-v3）
   - 例：開啟某些 Faster-Whisper 的「early return」選項
3. Cyberon 復用時程？若短期內 Cyberon 可恢復，是否建議我們暫時切回 `:8890`？

## Issue #2：110LLM 第一次 `/input` 偶爾回空白 outputs

### 觀察日

- 2026-05-13（首次發現，「你好，我要報案」場景）
- 2026-05-28（再次發生，「你好，我要檢舉」場景）

### 現象

caller 在通話開始說完第一句後，110LLM 收到 `/session/{id}/input` 請求，HTTP 200 OK 但 `outputs: []`（空陣列），導致機器A 沒有 AI 回覆可播。
使用者以為系統沒收到，重複再說一次，第二次才正常收到回覆。

### 機器A 側已採取的措施

- 收到空白 outputs 時印 `ℹ️ NLP 回空白` log 標記
- 清除 `nlp_pending` 旗標，允許後續 STT 繼續送出
- 不重試（避免無限循環）

### 實測 Log（5/28 案例）

```
14:29:18  🔇 VAD 靜音 800ms，送 stop
14:29:19  📝 STT FINAL：你好，我要檢舉。
14:29:22  📤 送 NLP：你好，我要檢舉。     ← 第 1 次 /call/stt
14:29:27  ℹ️ NLP 回空白（針對：你好，我要檢舉。）  ← 5 秒後 110LLM 回空陣列
14:30:12  🔇 VAD 靜音 800ms（使用者重複說話）
14:30:17  📤 送 NLP：我要檢舉。           ← 第 2 次 /call/stt
14:30:21  🤖 受理員：請問需要哪類協助？   ← 第二次正常回
```

### 期望機器B 回覆

1. 第一次 `/input` 為何會回空白？session warm-up？分類失敗 fallback？
2. 是否能調整為「至少回一句通用回覆」（例如「請說明您要報案的內容」）取代空陣列？
3. 此問題出現頻率多高？是否與特定開場詞（「你好...」「我要...」）有關？
4. 5/13 案例中觀察到第二次回覆一次帶兩句（疑似第一次累積後合併），這是否仍是現行行為？
