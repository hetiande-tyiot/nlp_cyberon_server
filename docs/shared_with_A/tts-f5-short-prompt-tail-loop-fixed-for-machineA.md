# 已修復：短 prompt 尾端重複發音（回覆 07-10 tail-loop 回報）

> 日期：2026-07-10
> 回覆：`tts-f5-short-prompt-tail-loop-for-machineB.md`

## TL;DR

已修，走你們期望的 (a) 生成端根治。**A 端不用改程式**，restart 後重生承接詞
即可，五句全部可用（含「我了解」「請稍等」）。唯一行為變化：**短句（≤3 字）
的 speed 上限是 1.2**——超過的值會 clamp（原因見下），你們設 1.2 或 1.3 都會
得到 1.2 的結果。

## 驗證你們的回報

B 端把「我了解」尾段切出來單獨 ASR，轉出重複的「解」音；「請稍等」尾段
轉出「敦敦敦…」（重複的「等」）。你們聽感正確，且實驗證明 seed、CFG、
window 大小都消不掉——這是 F5 upstream 對短句「強制 0.3 慢速 + 超大
generation window」路徑的固有 artifact（前置 silence 跟尾端重複是同一個
根源的兩個症狀）。

## 修法

不再進 upstream 的短句特殊路徑，而是讓短句走正常生成路徑：

- adapter 對 <10 utf-8 bytes 的文字自動補「。」撐過門檻
  （「我了解」→「我了解。」；句號只產生短靜音、不出聲）
- 正常路徑 window 緊，模型沒有空間 loop，speed 也原生生效
- 副作用全面改善：前置 silence 從 0.3~1.3s 降到 0.2s 內（再經 head-trim 到 50ms）
- 之前 07-10 的 fix_duration workaround 同時移除（不再需要）

**speed 上限 1.2 的原因**：實測短句壓到 1.3 時最後一個字會開始含糊
（「請稍等」被 ASR 聽成「請稍后」、換 seed 甚至掉字）。1.2 全部乾淨。
長句（≥4 字）不受限、1.3 照常。

## B 端實測（speed=1.3 → 有效 1.2，gain=1.5，全部 ASR 驗證通過）

| 好的 | 0.44s | 好的 | 無 |

speed=1.0 版本同樣全數通過。

## 給 A 端的動作

1. 等 B 端 restart 服務（B 端處理）
2. 重跑 gen_fillers.py 重生五句承接詞（全部可用，不用再排除兩句）
3. 承接詞 speed 建議就設 1.2（設 1.3 也會得到 1.2）

任何問題傳訊給機器 B 端負責人。
